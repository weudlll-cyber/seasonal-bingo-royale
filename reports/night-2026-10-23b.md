- **Rollback keeps one unencrypted database dump** (root only, `/var/lib/sbr/<env>/pre-update.dump`, replaced by the next update), because the encrypted backups can only be opened with your private key, which never stays on the server.
- **A restore on the server needs your age key file for a moment** (`sbr restore <file> --identity <file>`); copy it up, restore, delete it.
- **Website installs trust the website's Caddy by its address**; if the website's Caddy is recreated with a new address, `sbr status` says so and re-running the installer updates it.
- **SMTP settings are stored but not used yet**: the app sends no e-mail so far (e-mail verification is behind a flag).

- **Install source until releases exist**: the installer builds the image on the server from the branch `feat/vps-install` (a few minutes, needs internet for packages). Once you merge, the default ref should become `master` or a tag.
- **Standalone installs trust any private address as the proxy** (`SBR_TRUSTED_PROXIES=uniquelocal`): the app publishes no port, so only containers on the server reach it; Caddy's address is not fixed in advance.
- **The client bundle still contains the inactive dev sign-in menu and Quick Test code** (switched off, and their server routes do not exist in production).
- **Test accounts in throw-away databases**: in the install test, registering is limited to 5 an hour per address; two accounts from failed attempts stayed in the first test machine's database until the machine and its volumes were removed.

## FOR THE OWNER

**Game fixes (branch `feat/real-game-draft`).** In the lobby you can now abort a match with a reason (players then see the "cancelled" page). While an automatic start waits for players, the line says "Waiting for players — at least 2 are needed to start". At each round start every player's screen now gets only their own cards — and no longer the order of the numbers still to come, which was visible in the browser before. At 200 players that is 5 KB instead of 76 KB per screen per round; screens stay within half a second. A late screen update could put your console back to "running" after a match had finished; fixed.

**What you prepare (both types).** A VPS with Ubuntu 24.04 (good: 4 CPU, 8 GB RAM, 100 GB; smallest: 2 CPU, 4 GB, 20 GB free). On your Windows PC an SSH key (`ssh-keygen -t ed25519`) and an age key for the backups (`winget install FiloSottile.age`, then `age-keygen -o $HOME\sbr-age-key.txt` — it shows `Public key: age1…`; keep the file safe, it is the only way to open the backups). For standalone: a domain with an A record pointing at the VPS. For the website type: the website already running on the VPS.

**Installing standalone, step by step.** 1. `ssh root@<VPS>`. 2. `git clone --branch feat/vps-install https://github.com/weudlll-cyber/seasonal-bingo-royale.git sbr && sudo bash sbr/ops/install.sh`. 3. Answer: standalone, prod, your domain, your e-mail, your age public key, SMTP empty. 4. Wait for "Done" (it installs Docker and builds the game, a few minutes). 5. `sudo sbr admin create-super` (e-mail, name, password). 6. Open `https://<your domain>/`.

**Installing inside the website, step by step.** 1. `ssh root@<VPS>`. 2. The same command with `--type website` at the end. 3. Answer: prod, e-mail, age key (it finds the website's domain itself; if the website is not running it stops and tells you). 4. Do the four short steps it prints once in the website's checkout: copy `/opt/sbr/website-bingo.caddy` to `deploy/site/routes/bingo.caddy`, add `import /etc/caddy/routes/*.caddy` inside the site block of `deploy/site/Caddyfile`, add the volume `./routes:/etc/caddy/routes:ro` to the website's caddy service, `docker compose up -d caddy`. 5. `sudo sbr admin create-super`. 6. Open `https://<website domain>/games/bingo/`. Players use the game's own accounts for now.

**How backups reach your PC.** Every night at 03:30 the server writes an encrypted backup to `/var/backups/sbr/prod/` (14 daily and 8 weekly are kept). On your PC run `powershell -ExecutionPolicy Bypass -File ops\pull-backups.ps1 -Server root@<VPS>`; it copies only the new ones into `Documents\sbr-backups\prod`. Check one now and then with `sbr restore --drill <file> --identity <your key file>` (copy the key up, run, delete it again) — it restores into a throw-away database and counts what came back. Everything is in `docs/operator-guide.md`, with updating (`sbr update <ref>`), rolling back (`sbr rollback`), maintenance (`sbr maintenance on|off`) and the hardening checklist.

**What was tested and what not.** Tested for real on this PC, in throw-away Ubuntu 24.04 machines (containers with their own Docker): the standalone install on an IP address, run twice (the second run changed nothing), the first admin, a full match over the WebSocket, update, backup, restore drill, status, maintenance and rollback; the website install behind a stand-in of the website's Caddy, with a full match at `/games/bingo/`, no port of its own, and the clear stop when the website is missing. The test found and fixed three install bugs (HTTPS by IP address, Caddy not seeing a changed config, a clean-up error after the drill). Not tested: a real restore, the pull scripts against a real server, Let's Encrypt with a real domain, staging next to prod. Nothing is merged or published.
